## 1. Jelaskan alur yang terjadi ketika pengguna membuka halaman portofolio baru, mulai dari permintaan yang diterima proyek hingga data ditampilkan pada browser. Dalam jawabanmu, jelaskan peran urls.py proyek, urls.py aplikasi, view, model, dan template.

Pertama, pengguna menginisiasi suatu *request* ketika mengetikkan URL, misalnya dalam kasus website saya itu saya ambil `/education/` dari `muhammad-ghazi51-myportfolio.pws.cs.ui.ac.id/education/`. *Request* ini pertama kali diterima oleh `urls.py` yang ada di root folder project (`myportfolio/urls.py`). Setelah itu, file `urls.py` ini akan melihat URL itu dan meneruskannya ke `urls.py` yang ada di main (`main/urls.py`). Di dalam `main/urls.py`, Django mencocokkan pola URL ini dengan `urlpatterns` yang didaftarkan. Untuk kasus `/education/`, karena path dari pengguna cocok dengan path yang didaftarkan, file `urls.py` ini akan memanggil fungsi view `show_education` yang akan menangani halaman itu. Jika URL yang di-*request* itu tidak tersedia dalam file `urls.py` (misal `/random-page-yang-eksistensinya-dipertanyakan/`), `urls.py` akan bingung dan akan mengeluarkan error code 404: Page Not Found.

Lalu, setelah `show_education` itu dipanggil, file `views.py` (lokasi function `show_education`) akan menangani *request* ini. Fungsi ini memanggil `models.py` untuk meminta data seputar models yang didaftarkan pada proyek ini. Dalam kasus `show_education`, function ini melakukannya dengan `education_list = Education.objects.all().order_by("-started_at")`. Intinya, `education_list` memanggil seluruh object dari model `Education` yang diurutkan berdasarkan waktu dimulainya kursus/jenjang pendidikan itu. Saat mengambil data, `views.py` meminta model `Education` untuk mengambil semua data riwayat pendidikan yang terdaftar dari database (PostgreSQL saat `PRODUCTION`, SQLite untuk `localhost`). Model ini kemudian menerjemahkan perintah Python menjadi perintah SQL, mengambil data yang dihasilkan dari query itu, dan mengembalikannya ke function `show_education` di `views.py` untuk digunakan.

Setelah `views.py` mendapatkan data melalui `show_education` dari model, data itu akan dibungkus ke dalam *dict* bernama context. Lalu, `views.py` mengirimkan context ini ke file HTML yang berfungsi sebagai template laman itu. Setelah data diterima education.html, data itu disisipkan ke struktur HTML yang dibuat untuk menghasilkan halaman HTML yang utuh dan final. Hal ini dilakukan dengan Django Template Language (contoh: `{% for edu in education_list %}`). Setelah template selesai merakit HTML seutuhnya, Django mengirimkan HTML yang rapi itu kembali ke browser pengguna sebagai sebuah HTTP Response, yang kemudian menerjemahkan HTML dan CSS file sehingga website tampil di layar pengguna.

## 3. Apa perbedaan fungsi makemigrations dan migrate pada Django? Berikan contoh perubahan model yang mengharuskanmu menjalankan kedua perintah tersebut.

Fungsi `makemigrations` berfungsi untuk memindai atau mendeteksi semua perubahan yang kita buat pada `models.py`, seperti membuat model baru, menambahkan atribut, atau menghapus field dan mencatatnya dalam file baru dalam folder `main/migrations/`. File ini berisi instruksi dalam Python tentang apa saja yang berubah. Perlu ditekankan bahwa pada tahap `makemigrations` ini, database belum disentuh sama sekali, dan `makemigrations` ibarat hanyalah suatu *blueprint* saja untuk database.

Di sisi lain, `migrate` berfungsi untuk membaca file migration yang sudah dibuat `makemigrations`, menerjemahkan ke bahasa SQL, lalu mengeksekusinya langsung di sistem database (PostgreSQL saat `PRODUCTION` di PWS, atau SQLite di `localhost`). Kalau tadi kita misalkan `makemigrations` sebagai *blueprint*, `migrate` itu adalah bentuk eksekusinya yang benar-benar mengubah sesuatu dalam database, seperti membuat tabel baru atau sebagainya.

Untuk contoh perubahan model yang saya alami sendiri, saya akan ungkit lagi masalah yang saya alami pada Minggu, 13/9 siang, di mana saya melakukan commit dan push berulang kali ke PWS. Awalnya, setelah melakukan riset dan bertanya ke Generative AI, saya menyimpulkan bahwa menggunakan library Pillow akan lebih mudah untuk menampilkan karya-karya milik saya. Namun, setelah mendalami dan mencoba secara langsung di website, saya merasakan efek batasan penyimpanan di server PWS karena seluruh foto yang saya masukkan ke model hanya menunjukkan *alt text*-nya saja. Pada akhirnya, saya memilih untuk mengubah ImageField menjadi `image_url` yang menggunakan `CharField` di file `models.py` yang hanya perlu menyimpan url dari file yang ada di `/static/img/` untuk menghindari masalah-masalah yang saya alami tadi. 

Kalau saya hanya cuma mengubah `models.py` saja, database tidak akan tahu kalau ada sesuatu yang berubah dan pastinya akan error jika saya deploy. Oleh karena itu, saya jalankan `python manage.py makemigrations` agar Django merekam perubahan pada model ke riwayat migrasi dalam `main/migrations/`. Setelah file migrasi dibuat oleh perintah `makemigrations` itu, saya jalankan `python manage.py migrate` agar perubahan yang saya buat itu membuat databasenya juga berubah, sehingga `image` yang lama bisa dihapus dan digantikan oleh `image_url`.
